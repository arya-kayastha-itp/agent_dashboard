# FinOps Agent — Consolidated Plan

> Planning document only — nothing here has been built yet. Mirrors the
> style of ARCHITECTURE.md / PROJECT_OVERVIEW.md so it can sit alongside
> them once implementation starts.

## 1. Scope

A new capability layered onto the existing Agent Dashboard: monitors API
and token usage across **all** tracked agents and raises alerts when a
call is expensive or when an agent's calls are failing frequently.
Follows the app's existing conventions — layered backend (migration →
validator → service → controller → route) and layered frontend
(api-wrapper → hook → page).

## 2. Data source & ingestion

- Usage data comes from log entries generated by the external apps that
  call each agent's API — there's no gateway sitting in front of those
  calls today, so ingestion is push-based.
- Each app **self-reports its own `agentId`** on every log entry. No auth
  on this endpoint yet — same "no auth" state as the rest of the app.
  Flagged as a follow-up: per-project ingestion tokens once auth exists
  elsewhere, so the server derives `agentId` instead of trusting the payload.
- Two endpoints:
  - `POST /api/finops/usage-logs` — one call, one log.
  - `POST /api/finops/usage-logs/batch` — for apps that buffer and flush.
    **Not** all-or-nothing like `updates/batch` — each entry is its own
    transaction, so one malformed entry doesn't discard the rest.
- The payload does **not** include cost. Apps send only token counts —
  cost is computed server-side (see §5).
- Errors are categorized at the source into two kinds:
  - `api_error` — the agent's own API failed (5xx, timeout, rate limit).
  - `validation_error` — the calling app made a mistake (bad params,
    failed validation).

## 3. Data model

### `api_usage_logs`
One row per API call.

| Column | Notes |
|---|---|
| `id`, `agent_id` (FK) | |
| `request_id`, `endpoint`, `model` | |
| `tokens_input`, `tokens_output`, `tokens_total` | |
| `status` | `success` \| `error` |
| `error_category` | `api_error` \| `validation_error`, null on success |
| `error_code` | freeform detail, optional |
| `cost_usd` | **computed**, not sent by the caller — nullable if unpriced |
| `latency_ms`, `source`, `occurred_at`, `created_at`, `raw_metadata` | |

Indexes: `(agent_id, occurred_at desc)`, `(agent_id, status, occurred_at desc)`.

### `model_pricing` — NEW, effective-dated

| Column | Notes |
|---|---|
| `id`, `model` | |
| `input_price_per_1k_tokens`, `output_price_per_1k_tokens` | |
| `effective_from` | timestamp — this price applies from this point forward |
| `created_at`, `created_by` | audit trail, since there's now an admin UI editing this |

No uniqueness constraint on `model` — each row is a new price point in
time. Cost lookup for a log on model X at time T = the row for X with
the latest `effective_from <= T`. This keeps historical charts accurate
after a price change instead of re-pricing old calls at today's rate.

**Admin UI**: `/finops/pricing` — table of models with price history, a
form to add a new effective-dated price. Full CRUD, not just an API.

### `finops_thresholds` — NEW, generic (not fixed-column)

| Column | Notes |
|---|---|
| `id` | |
| `agent_id` | nullable — null = global default |
| `alert_type` | varchar — see §4, open-ended |
| `threshold_value` | numeric; meaning depends on `alert_type` ($ for `expensive_call`, % for error-rate types) |
| `window_minutes` | nullable — only meaningful for error-rate types |
| `created_at`, `updated_at` | |

Chosen as a generic `(agent_id, alert_type, value, window)` shape instead
of one column per threshold specifically so a new alert type in the
future doesn't require a migration.

**Admin UI**: `/finops/thresholds` — mirrors the pricing page. Table of
thresholds by agent + alert type, form to add/edit (agent picker, alert
type picker, value, window).

### `finops_alerts`

| Column | Notes |
|---|---|
| `id`, `agent_id` | |
| `alert_type` | `expensive_call` \| `unpriced_usage` \| `high_api_error_rate` \| `high_validation_error_rate` |
| `severity` | `warning` \| `critical` |
| `message`, `details` (jsonb) | |
| `status` | `open` \| `acknowledged` \| `resolved` |
| `created_at`, `resolved_at` | |

## 4. Alert types & delivery

| Alert type | Trigger | Delivery |
|---|---|---|
| `expensive_call` | A single call's computed cost or token count exceeds its threshold | in-app + email |
| `unpriced_usage` | A call used a model with no matching pricing row (cost unknown) | **in-app only** — an ops todo, not an incident |
| `high_api_error_rate` | % of calls with `error_category = api_error` in the window exceeds threshold | in-app + email |
| `high_validation_error_rate` | % of calls with `error_category = validation_error` in the window exceeds threshold | in-app + email |

Each type dedupes independently (no repeat "open" alert of the same
type/agent while one's already open within the window). Threshold
resolution order: per-agent override → global default → hardcoded fallback.

## 5. Cost computation flow

Runs inside the same transaction that inserts the usage log (mirrors
`recordUpdate`'s pattern of one place that writes and keeps things consistent):

1. Insert the log row — tokens, status, error category. No cost yet.
2. Look up `model_pricing` for `(model, occurred_at)` — latest `effective_from <= occurred_at`.
3. **Found** → compute `cost_usd = tokens_input × input_rate + tokens_output × output_rate`, store it.
4. **Not found** → leave `cost_usd` null, raise/dedupe an `unpriced_usage` alert (in-app only).
5. Evaluate `expensive_call` — only possible when cost is known.
6. Evaluate `high_api_error_rate` and `high_validation_error_rate` independently, each against its own threshold + window.

## 6. API surface (planned)

- `POST /api/finops/usage-logs` — ingest one log
- `POST /api/finops/usage-logs/batch` — ingest many (per-entry results, 207 on partial failure)
- `GET /api/finops/usage`, `GET /api/finops/usage/summary` — usage/cost charts
- `GET /api/finops/alerts`, `PATCH /api/finops/alerts/:id` — alert list + acknowledge/resolve
- `GET/POST /api/finops/pricing` — list & add pricing rows (backs the pricing admin page)
- `GET/PUT /api/finops/thresholds` — list & set thresholds (backs the thresholds admin page)

## 7. Frontend surfaces (planned)

- `/finops` — usage/cost chart + alerts list, tabbed by status
- `/finops/pricing` — admin: model price history + add-new-price form
- `/finops/thresholds` — admin: thresholds by agent + alert type, add/edit form
- Global alert bell in the `AppBar` (in-app delivery), polling every 30s — no push channel exists elsewhere in this app

## 8. Known trade-offs / deferred items

- **No auth on ingestion** — relies on each app self-reporting the
  correct `agentId`. Follow-up once auth exists elsewhere: per-project
  ingestion tokens, server derives `agentId` instead of trusting the payload.
- **No background job queue** — alert emails send synchronously, wrapped
  so a delivery failure never breaks the ingestion request.
- **Polling, not push** — matches the rest of this app's simplicity; a
  websocket/SSE channel would be the natural upgrade if this matters more later.
- **Batch ingestion is per-entry, not all-or-nothing** — deliberate,
  since these are independent telemetry facts, not two tables that must
  stay in sync the way `agents`/`agent_updates` do.
